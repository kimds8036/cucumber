# 타이머 기능 전체 검증 결과 (현재 코드 기준)

코드 수정 없이 현재 구현을 추적한 분석 결과입니다.

---

## A. 기본 흐름

### A1. 앱 최초 실행 → 타이머 시작 → 정지 → 저장
- 현재 코드 동작 흐름
  - 페이지 진입 시 `timer.jsx`의 초기 `useEffect`에서 `loadDayFromDb(todayKey)` 호출 후 상태 복원.
  - 시작: `startTimerTop()` -> `sessions`에 open 세션 추가(`endSeconds=null`) -> `setStartTimestamp(Date.now())` -> `emitTimerStatus('studying')`.
  - 정지: `pauseTimer()` -> `endCurrentSession()`(ms 누적) -> `closeOpenSession()`(open 세션 endSeconds 채움) -> `requestImmediatePersist('pause')`.
  - 저장: 즉시저장 effect에서 `persistTimerSnapshot('pause')` -> `saveDayToDb` -> 백엔드 `POST /api/timer/day`.
- 오류 가능성 있는 부분
  - **정상(핵심 흐름)**.
  - 단, 프론트는 ms 단위, 백엔드는 seconds 기반 재계산이므로 세션당 최대 1초 내외 미세 오차 가능.
- 의심 코드 위치
  - `frontend/view/src/timer.jsx`: `startTimerTop`, `pauseTimer`, `endCurrentSession`, 즉시저장 effect
  - `frontend/utils/timerStorage.js`: `saveDayToDb`
  - `back/src/routes/timer.js`: `POST /day`의 `SUM(...)`

### A2. 과목 선택 후 시작 → 다른 과목으로 전환 → 정지
- 현재 코드 동작 흐름
  - 과목 시작: `startForSubject(subjectId)`로 open 세션 생성.
  - 과목 전환: 실행 중이면 기존 세션 `endCurrentSession + closeOpenSession`으로 닫고 `requestImmediatePersist('subject-switch')`, 이후 새 과목 open 세션 생성.
  - 정지: A1과 동일.
- 오류 가능성 있는 부분
  - **정상**.
  - 연속 탭 매우 빠를 때 저장 요청이 연달아 발생해도 `persistChainRef` 직렬화로 순서 보장.
- 의심 코드 위치
  - `frontend/view/src/timer.jsx`: `startForSubject`, `startTimerTop`, `persistTimerSnapshot`

### A3. 타이머 실행 중 같은 화면 내 다른 탭(할일 등) 이동 후 복귀
- 현재 코드 동작 흐름
  - 같은 타이머 화면 내부 스크롤/섹션 이동은 타이머 상태 영향 없음.
  - 실시간 표시는 `LiveElapsedTicker`의 `setInterval(1s)` + `Date.now()-startTimestamp`.
- 오류 가능성 있는 부분
  - **정상**.
- 의심 코드 위치
  - `frontend/view/src/timer.jsx`: `LiveElapsedTicker`

## B. 백그라운드 관련

### B1. 타이머 실행 중 홈버튼 → 5분 후 복귀
- 현재 코드 동작 흐름
  - 백그라운드 진입: `persistTimerSnapshot('app-background')`, 진입시각 기록.
  - 복귀: 15분 미만이면 `setStartTimestamp(prev + backgroundMs)` 보정.
- 오류 가능성 있는 부분
  - **정상(뻥튀기 방지 동작)**.
- 의심 코드 위치
  - `frontend/view/src/timer.jsx`: AppState effect(`backgroundMs` 계산, `setStartTimestamp(prev+backgroundMs)`)

### B2. 타이머 실행 중 홈버튼 → 20분 후 복귀 (auto-close)
- 현재 코드 동작 흐름
  - 복귀 시 `backgroundMs >= 15분`이면 `POST /api/timer/session/close-incomplete` 호출.
  - 프론트에서도 현재 세션을 닫고(`endCurrentSession`, `closeOpenSession`) `isRunning=false`.
- 오류 가능성 있는 부분
  - **주의 필요**: 이 분기에서는 `requestImmediatePersist('pause')`를 쓰지 않으므로 프론트 로컬 상태와 서버 반영 시점이 잠깐 어긋날 수 있음(서버는 close-incomplete로 이미 닫힘).
  - 기능적으로는 큰 문제 없이 idle로 정리됨.
- 의심 코드 위치
  - `frontend/view/src/timer.jsx`: AppState effect의 auto-close 분기
  - `back/src/routes/timer.js`: `POST /session/close-incomplete`
  - `back/src/socket/socketService.js`: `closeIncompleteStudySessions`

### B3. 타이머 정지 상태에서 백그라운드 → 복귀
- 현재 코드 동작 흐름
  - `wasRunningOnBackgroundRef.current=false`라 복귀 시 보정/auto-close 로직 미실행.
- 오류 가능성 있는 부분
  - **정상**.
- 의심 코드 위치
  - `frontend/view/src/timer.jsx`: AppState effect

### B4. 타이머 실행 중 백그라운드 → 백그라운드 중 오전 6시 통과 → 복귀
- 현재 코드 동작 흐름
  - 백그라운드 진입 시 `backgroundDayKeyRef` 저장.
  - 복귀 시 dayKey 변경 감지되면 `performTimerDayRollover(...)` 우선 실행(보정/auto-close보다 우선).
- 오류 가능성 있는 부분
  - **주의 필요**: day rollover가 발생하면 15분 초과 auto-close 분기보다 rollover가 우선되어, 장시간 백그라운드였어도 자동종료 대신 새 day open 세션으로 이어짐.
- 의심 코드 위치
  - `frontend/view/src/timer.jsx`: AppState effect의 `backgroundDayKey` 비교 분기, `performTimerDayRollover`

## C. Day Rollover

### C1. 포그라운드에서 타이머 실행 중 오전 6시 도달 (1분 폴링 감지)
- 현재 코드 동작 흐름
  - `checkDayChange`(1분 주기)에서 dayKey 변경 감지.
  - 실행 중이면 `performTimerDayRollover`:
    - 이전 open 세션 `endSeconds=86400`으로 닫아 flush 저장
    - 새 dayKey로 전환, `totalElapsedMs=0`
    - 새 open 세션 `startSeconds=0`, `startTimestamp=Date.now()`
- 오류 가능성 있는 부분
  - **정상**(스펙 부합).
  - 단, 폴링이므로 감지 지연(최대 약 1분)은 구조적 특성.
- 의심 코드 위치
  - `frontend/view/src/timer.jsx`: `checkDayChange`, `performTimerDayRollover`

### C2. 오전 5시 50분 시작 → 6시 10분 정지
- 현재 코드 동작 흐름
  - 6시 이후 첫 폴링에서 day rollover로 세션 분리.
  - 정지 시 새 day open 세션 닫고 저장.
- 오류 가능성 있는 부분
  - **정상**.
- 의심 코드 위치
  - `frontend/view/src/timer.jsx`: `performTimerDayRollover`, `pauseTimer`

### C3. 오전 5시에 시작 → 백그라운드 → 오전 7시에 복귀
- 현재 코드 동작 흐름
  - 복귀 시 dayKey mismatch로 rollover 실행.
- 오류 가능성 있는 부분
  - **주의 필요**: B4와 동일하게 장시간 백그라운드라도 rollover 우선으로 처리되어 auto-close 정책보다 강하게 동작.
- 의심 코드 위치
  - `frontend/view/src/timer.jsx`: AppState 복귀 분기, `performTimerDayRollover`

## D. 데이터 저장/조회 일관성

### D1. 정지 시 saveDayToDb 호출 → 백엔드 재계산 → 프론트 표시값 일치 여부
- 현재 코드 동작 흐름
  - 프론트 정지 시 즉시 저장 요청.
  - 백엔드는 세션 합으로 `total_elapsed_ms`를 재계산해 저장.
- 오류 가능성 있는 부분
  - **대체로 정상**.
  - ms(프론트) vs sec(백엔드) 단위 차이로 미세 오차 가능.
- 의심 코드 위치
  - `frontend/view/src/timer.jsx`: `pauseTimer`, 즉시저장 effect
  - `back/src/routes/timer.js`: `SUM(...) total_ms`

### D2. 과목별 시간 합산 vs 전체 시간(total_elapsed_ms) 일치 여부
- 현재 코드 동작 흐름
  - 과목별은 프론트에서 `displaySessions` 필터/합산.
  - 전체는 `totalElapsedMs` 또는 백엔드 재계산값.
- 오류 가능성 있는 부분
  - **부분 불일치 가능(설계상)**:
    - 과목 미지정 세션(`subjectId=null`)은 과목합에 빠짐.
    - 실행 중 세션은 과목합에 즉시 반영 방식이 다름.
- 의심 코드 위치
  - `frontend/view/src/timer.jsx`: `getSubjectTotalMs`, `displayTotalMs` 계산

### D3. 진행 중 세션(end_seconds=NULL)이 total_elapsed_ms 계산에 포함되는지
- 현재 코드 동작 흐름
  - 백엔드 집계 SQL에서 `end_seconds IS NULL THEN 0`.
- 오류 가능성 있는 부분
  - **정상(미포함)**.
- 의심 코드 위치
  - `back/src/routes/timer.js`: `POST /day` 집계 CASE

### D4. 같은 dayKey로 여러 번 saveDayToDb 호출 시 중복 세션 생성 여부
- 현재 코드 동작 흐름
  - 백엔드에서 `(subject_id,start_seconds,end_seconds)` 및 open 세션 조건으로 중복 방지 로직 수행.
- 오류 가능성 있는 부분
  - **대체로 정상**.
  - 다만 클라이언트가 startSeconds가 다른 유사 세션을 보내면 별도 세션으로 저장될 수 있음(현재 프론트는 보통 고정 startSeconds 사용).
- 의심 코드 위치
  - `back/src/routes/timer.js`: `dedupeSessionsPreferClosed`, open/existing 조회 후 insert 분기

## E. 소켓 관련

### E1. 타이머 시작/정지 시 소켓 이벤트와 REST 저장 순서/충돌 여부
- 현재 코드 동작 흐름
  - 시작/정지는 프론트 로컬 상태 + 소켓 emit 즉시.
  - DB 저장은 REST(`saveDayToDb`) 경로(즉시/주기/배경 flush)로 별도 처리.
- 오류 가능성 있는 부분
  - **충돌 리스크 낮음**(소켓 DB write 제거됨).
- 의심 코드 위치
  - `frontend/hooks/useSocketEvents.js`: `emitTimerStatus`
  - `frontend/view/src/timer.jsx`: 저장 트리거 effect

### E2. 소켓에서 세션 DB 저장 로직 완전 제거 여부
- 현재 코드 동작 흐름
  - `friendEvents`의 `friend_timer_status`는 `broadcastTimerStatus`만 수행.
  - `upsertStudySessionStart/closeStudySession` 호출 없음.
- 오류 가능성 있는 부분
  - **정상(제거 완료)**.
- 의심 코드 위치
  - `back/src/socket/friendEvents.js`: `friend_timer_status` 핸들러

### E3. 친구 공부 상태 표시(초록점) 정상 동작 여부
- 현재 코드 동작 흐름
  - 실시간 온라인 친구: 소켓 `friend_timer_status` 브로드캐스트로 즉시 반영 가능.
  - REST 보강(`getStudyingFriends`)은 DB `study_sessions end_seconds IS NULL` 기준.
- 오류 가능성 있는 부분
  - **주의 필요**: 소켓 DB 저장 제거 후에는 DB가 REST 저장 타이밍(정지/5분 주기/백그라운드 flush)에 의존하므로, 앱 재진입/재연결 시점엔 REST 결과가 지연될 수 있음.
- 의심 코드 위치
  - `back/src/socket/socketService.js`: `broadcastTimerStatus`, `getStudyingFriends`
  - `frontend/view/src/timer.jsx`: `useFocusEffect`의 `refreshStudyingFriends`

## F. 색칠 표 렌더링

### F1. end_seconds=86400 세션이 마지막 슬롯까지 색칠되는지
- 현재 코드 동작 흐름
  - `toTimerDayEndAwareSeconds`로 86400 허용.
  - 슬롯 겹침 계산에서 `overlap`으로 마지막 슬롯까지 반영.
- 오류 가능성 있는 부분
  - **정상**.
- 의심 코드 위치
  - `frontend/view/src/timer.jsx`: `toTimerDayEndAwareSeconds`, `getSlotSegments`(두 곳)

### F2. 과목 없는 세션(subject=null) 색상 처리
- 현재 코드 동작 흐름
  - `resolveSessionColor`: linked color 없으면 `session.subjectColor`, 없으면 `TIMETABLE_GRAY`.
- 오류 가능성 있는 부분
  - **정상**.
- 의심 코드 위치
  - `frontend/view/src/timer.jsx`: `resolveSessionColor`

### F3. 동일 시간대 세션 겹침 렌더링
- 현재 코드 동작 흐름
  - segments를 시작순 정렬 후 같은 셀 내 순차 flex로 그림.
- 오류 가능성 있는 부분
  - **주의 필요**: 진짜 겹치는 세션이 존재하면(데이터 이상/중복) 시각적 겹침 표현이 아니라 순차 덧칠 형태라 왜곡 가능.
- 의심 코드 위치
  - `frontend/view/src/timer.jsx`: `getSlotSegments` + segment 렌더 루프

### F4. 맞는 시간대에 제대로 색칠되는지
- 현재 코드 동작 흐름
  - 세션 시간은 "6시 기준 경과초"(0~86400).
  - 타임테이블 슬롯 시작값은 `hour * 3600` 사용 (`hour=(6+row)%24`).
- 오류 가능성 있는 부분
  - **높은 위험(시간대 오프셋 의심)**:
    - 6시 기준 경과초(0=06:00)와 슬롯 기준(06행=21600) 좌표계가 다르게 섞여 있어 색칠 위치가 실제 시간대와 어긋날 가능성이 큼.
- 의심 코드 위치
  - `frontend/view/src/timer.jsx`: `renderTimetable`의 `slotStartBaseSeconds = hour * 3600`
  - `frontend/view/src/timer.jsx`: `getSecondsFromSixAM`, `toTimerDayTimelineSeconds`

## G. 타이머 페이지 진입 시 데이터 로드 검증

- 현재 코드 동작 흐름
  - 진입 시 `loadDayFromDb(todayKey)`로 오늘 데이터 조회.
  - 성공 시 `sessions/totalElapsedMs/subjects/tasks` 세팅.
  - open 세션 있으면 `startTimestamp` 복구(ghost 세션 >1시간은 실행중 복구 안함).
  - 날짜 선택 변경 시 `loadDayData(selectedDayKey)`로 해당 day 조회.
- 오류 가능성 있는 부분
  - **대체로 정상**.
  - 주의:
    - ghost open 세션은 실행 복구를 막지만, 서버 세션이 열린 채 남아 있을 수 있어 정리 타이밍(별도 close-incomplete)에 의존.
    - `loadDayFromDb` 401이면 null 반환 처리라 비로그인 상태에서는 빈 화면 동작.
- 의심 코드 위치
  - `frontend/view/src/timer.jsx`: 초기 로드 effect, selectedDayKey 로드 effect
  - `frontend/utils/timerStorage.js`: `loadDayFromDb`

## 종합 판단

- 핵심 타이머 저장/rollover/백그라운드 보정 흐름은 전반적으로 의도대로 동작.
- 현재 가장 큰 리스크는 **F4(시간표 색칠 시간축 좌표계 불일치 가능성)**.
- 그다음 리스크는 **소켓 DB저장 제거 이후 REST 기반 친구 상태 보강 지연(E3)**, **rollover가 auto-close 우선순위를 덮는 케이스(B4/C3)**.
