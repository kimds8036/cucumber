# 타이머/공부기록 DB 스키마 재점검

현재 코드 기준(마이그레이션 + 서버 로직)으로 타이머/공부기록 DB 구조와 저장 방식은 아래와 같습니다.

## 1. 타이머/세션/공부기록 관련 테이블 전체

### study_days (일별 요약)
- `id` INT AUTO_INCREMENT PRIMARY KEY
- `user_id` INT NOT NULL  
  - FOREIGN KEY -> users(id) ON DELETE CASCADE
- `day_key` DATE NOT NULL (YYYY-MM-DD)
- `total_elapsed_ms` BIGINT NOT NULL DEFAULT 0 (해당 날짜 총 공부 시간, ms)
- `subjects` JSON NULL (레거시 과목 JSON)
- `tasks` JSON NULL (레거시 할일 JSON)
- `created_at` TIMESTAMP DEFAULT CURRENT_TIMESTAMP
- `updated_at` TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
- 제약/인덱스:
  - UNIQUE KEY `unique_user_day (user_id, day_key)`
  - INDEX `idx_user_id (user_id)`
  - INDEX `idx_day_key (day_key)`

### study_sessions (세션 원장)
- `id` INT AUTO_INCREMENT PRIMARY KEY
- `user_id` INT NOT NULL  
  - FOREIGN KEY -> users(id) ON DELETE CASCADE
- `day_key` DATE NOT NULL
- `subject_name` VARCHAR(100) NULL
- `subject_id` BIGINT NULL  
  - FOREIGN KEY -> timer_subjects(id) ON DELETE SET NULL
- `subject_color` VARCHAR(20) NULL (세션 시점 스냅샷)
- `start_seconds` INT NOT NULL (해당 day 기준 시작 초)
- `end_seconds` INT NULL (종료 초, NULL이면 진행 중)
- `created_at` TIMESTAMP DEFAULT CURRENT_TIMESTAMP
- 제약/인덱스:
  - INDEX `idx_user_day (user_id, day_key)`
  - INDEX `idx_subject_name (subject_name)`
  - INDEX `idx_start_seconds (start_seconds)`
  - INDEX `idx_study_sessions_open (user_id, day_key, end_seconds)`
  - INDEX `idx_study_sessions_subject_id (subject_id)`
  - INDEX `idx_study_sessions_subject_color (subject_color)`

### timer_subjects (정규화 과목 메타)
- `id` BIGINT AUTO_INCREMENT PRIMARY KEY
- `user_id` INT NOT NULL  
  - FOREIGN KEY -> users(id) ON DELETE CASCADE
- `day_key` DATE NOT NULL
- `name` VARCHAR(100) NOT NULL
- `color` VARCHAR(20) NOT NULL
- `is_deleted` BOOLEAN NOT NULL DEFAULT FALSE
- `created_at` TIMESTAMP DEFAULT CURRENT_TIMESTAMP
- `updated_at` TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
- 인덱스:
  - INDEX `idx_timer_subjects_user_day (user_id, day_key)`
  - INDEX `idx_timer_subjects_user_day_deleted (user_id, day_key, is_deleted)`

### timer_tasks (정규화 할일)
- `id` BIGINT AUTO_INCREMENT PRIMARY KEY
- `user_id` INT NOT NULL  
  - FOREIGN KEY -> users(id) ON DELETE CASCADE
- `day_key` DATE NOT NULL
- `subject_id` BIGINT NULL  
  - FOREIGN KEY -> timer_subjects(id) ON DELETE SET NULL
- `content` VARCHAR(500) NOT NULL
- `status` ENUM('pending', 'done') NOT NULL DEFAULT 'pending'
- `is_deleted` BOOLEAN NOT NULL DEFAULT FALSE
- `created_at` TIMESTAMP DEFAULT CURRENT_TIMESTAMP
- `updated_at` TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
- 인덱스:
  - INDEX `idx_timer_tasks_user_day (user_id, day_key)`
  - INDEX `idx_timer_tasks_subject_id (subject_id)`

## 2. 시간 저장 방식 (timestamp/UTC/KST/duration 단위)

- 핵심 세션 시간은 `start_seconds` / `end_seconds`로 저장
  - 단위: 초(second)
  - 기준: "타이머 하루 시작점(오전 6시 KST)"부터 경과한 초 (0~86399)
- 총 공부시간은 `total_elapsed_ms`로 저장
  - 단위: 밀리초(ms)
  - 계산식: 각 세션 `(end_seconds - start_seconds) * 1000` 합계
- 타임존 기준
  - day/seconds 계산 로직은 코드에서 명시적으로 `Asia/Seoul`(KST) 사용
  - SQL에서도 `UTC_TIMESTAMP()`를 `CONVERT_TZ(..., '+09:00')` 후 초 계산
- `created_at/updated_at`은 `TIMESTAMP DEFAULT CURRENT_TIMESTAMP` 사용
  - 이 값의 물리 저장/표시는 DB 세션/서버 설정 영향 가능
  - 타이머 도메인 계산 자체는 KST 기준

## 3. "하루" 정의 기준

- `day_key`는 DATE 컬럼이며 문자열 `YYYY-MM-DD`로 취급
- 하루 경계는 KST 오전 6시
  - 오전 6시 이전은 전날 `day_key`
  - 오전 6시 이후는 당일 `day_key`
- 즉, 자정 경계가 아니라 06:00 KST 기준 day rollover

## 4. 과목별 시간 vs 전체 시간 저장 방식

- 전체 시간은 별도 저장: `study_days.total_elapsed_ms`
- 과목별 시간은 별도 합계 컬럼 없음
  - `study_sessions`의 `subject_id`(및 `subject_name/color`)로 세션 단위 기록 후 집계 계산
- `timer_subjects`는 과목 메타, `timer_tasks`는 할일 메타
  - 둘 다 과목별 누적 시간을 직접 저장하지 않음

## 5. 세션 시작/종료 기록 방식

- 기록 방식은 `start_seconds + end_seconds`
  - 시작 시 세션 INSERT (`end_seconds = NULL`)
  - 종료 시 해당 open 세션의 `end_seconds` UPDATE
- 진행 중 세션 판별은 `end_seconds IS NULL`
- duration만 단독 저장하지 않고 `(end - start)`로 계산
- 서버는 저장 시 `study_days.total_elapsed_ms`를 클라이언트 값이 아니라 세션 합계로 재계산해 반영

## 6. 타이머/공부시간 관련 백엔드 API 전체 분석 (현재 코드 기준)

### 1) 세션 저장 API (endpoint, request body, 저장 로직)

#### REST: `POST /api/timer/day` (하루 요약 + 세션 저장 핵심 API)
- Request body
  - `dayKey`: string(YYYY-MM-DD, 서버에서 앞 10자리로 정규화)
  - `sessions`: array
    - item: `{ id?, subjectId?, subjectName?, subjectColor?, startSeconds, endSeconds? }`
  - `totalElapsedMs`: number (클라 값은 참고만, 최종값은 서버 재계산)
  - `subjects`: array(정규화 과목 upsert용)
  - `tasks`: array(정규화 할일 upsert용)
- 저장 로직 요약
  - 트랜잭션 시작
  - `timer_subjects` upsert(없으면 insert, 있으면 update)
  - `timer_tasks` upsert(soft delete 고려)
  - `study_sessions` upsert
    - `id` 있으면 해당 row update 시도
    - 없으면 open 세션 매칭 후 close/update 또는 신규 insert
    - 중복 세션은 삽입 생략
  - 세션 합계로 `total_elapsed_ms` 서버 재계산:
    - `SUM(CASE ... ELSE (end_seconds - start_seconds) * 1000 END)`
  - `study_days`에 `INSERT ... ON DUPLICATE KEY UPDATE`로 반영
  - 커밋

#### 소켓 이벤트(REST 아님): `friend_timer_status`
- 수신 위치: 소켓 이벤트 핸들러(`friendEvents`)
- 상태별 처리
  - `status='studying'`:
    - `upsertStudySessionStart` 호출
    - 이전 미완료 세션 1건 `end_seconds`를 "현재 KST 기준 초"로 종료 후 신규 open 세션 insert
  - `status='idle'`:
    - `closeStudySession` 호출
    - 최신 open 세션 1건 종료
  - `status='heartbeat'`: 저장 처리 없음
- 참고: 실시간 상태 브로드캐스트까지 수행

#### 보조 REST
- `POST /api/timer/session/close-incomplete`
  - 유저의 미완료 세션이 있으면 종료 처리 (`end_seconds` 채움) + 상태 idle 브로드캐스트

### 2) 공부시간 조회 API (일별/과목별/전체)

#### 일별 조회
- `GET /api/timer/day?dayKey=YYYY-MM-DD`
  - 반환: `sessions`, `totalElapsedMs`, `subjects`, `tasks`
  - `totalElapsedMs`: `study_days.total_elapsed_ms`
  - `sessions`: `study_sessions` (day_key 기준)
  - `subjects/tasks`: 정규화 테이블 우선(`timer_subjects`, `timer_tasks`), 없으면 `study_days.subjects/tasks` fallback

#### 과목별 조회
- 전용 "과목별 합계 API"는 없음
- 현재 구조상 `GET /api/timer/day`의 `sessions`를 과목별(`subject_id`)로 클라이언트에서 집계하는 방식
- 과목 메타 조회는 동일 응답의 `subjects` 사용

#### 전체(기간/누적) 조회
- 사용자 개인의 누적 총합을 직접 반환하는 전용 API는 없음
- 학교 단위 집계는 별도 제공:
  - `GET /api/schools/me/study-grass`
  - `GET /api/schools/:schoolId/study-grass`
  - Redis 캐시된 일자별 `totalElapsedMs`, `activeUserCount` 시리즈 반환

### 3) 시간 계산을 프론트/백엔드 어디서 하는지

- 세션 단위 시간 기록(`startSeconds`, `endSeconds`)은 프론트/소켓 이벤트 입력 영향이 있음
- 최종 일별 총공부시간(`total_elapsed_ms`)은 백엔드가 세션 합으로 재계산해 저장
  - 즉, 핵심 합계 기준은 백엔드
- 과목별 합계는 백엔드 전용 API가 없어 실질적으로 클라이언트 집계 의존

### 4) "하루" 집계 쿼리 날짜 범위 기준

- 이 시스템은 `day_key`(DATE)를 기준으로 집계하며, 일반적인 `created_at BETWEEN 00:00~23:59` 범위를 쓰지 않음
- `day_key` 생성 기준이 "KST 06:00 경계"라서, 의미상 하루 범위는:
  - KST 06:00 ~ 다음날 05:59:59
- 실제 쿼리도 대부분 `WHERE day_key = ?` 형태로 조회/집계

### 5) 타임존 처리 방식 (UTC/KST)

- 타이머 도메인 시간 계산은 KST 기준으로 명시 구현
  - JS: `Intl.DateTimeFormat(..., timeZone: 'Asia/Seoul')`
  - SQL: `UTC_TIMESTAMP()` -> `CONVERT_TZ(..., '+09:00')` 후 초 계산
- 저장 형태
  - 세션 시각은 절대 timestamp가 아니라 `day_key + seconds-from-day-start` 방식
  - `created_at/updated_at`는 DB TIMESTAMP 기본값 사용(물리 저장/표시는 DB 설정 영향)
- 결론적으로 타이머 로직 자체는 "처음부터 KST 하루 모델"을 사용

### 6) 앱 백그라운드/복귀 시 세션 처리 로직 존재 여부

- 있음
  - REST `POST /api/timer/session/close-incomplete` 제공
  - 서버 함수 `closeIncompleteStudySessions`가 미완료 세션 종료 처리
- 소켓에서도 방어 로직 존재
  - 타이머 시작 시 기존 open 세션 자동 종료 후 새 세션 시작
  - 타이머 종료(idle) 시 open 세션 종료
- 배치 가드 존재
  - `timerSession.guard`가 오래된 미완료 세션(`created_at` 기준 stale) 자동 종료

## 7. 프론트엔드 타이머 관련 코드 전체 분석 (현재 코드 기준)

### 1) 타이머 시작/정지/재개 로직

- 핵심 상태
  - `isRunning`, `activeSubjectId`, `startTimestamp`, `sessions`, `totalElapsedMs`
- 시작(상단 시작 버튼)
  - `toggleTimer()` -> `startTimerTop()`
  - 이미 실행 중 다른 세션이면 기존 세션 종료 처리 후 새 open 세션 추가
  - `sessions`에 `{ startSeconds, endSeconds: null }` push
  - `startTimestamp = Date.now()` 설정
  - 소켓 `emitTimerStatus('studying', ...)` 전송
- 시작(과목별 시작 버튼)
  - `startForSubject(subjectId)`에서 동일하게 처리하되 `subjectId/subjectName/subjectColor` 포함
- 정지/일시정지
  - `pauseTimer()`
  - `duration = Date.now() - startTimestamp`를 `totalElapsedMs`에 누적
  - 현재 open 세션의 `endSeconds`를 현재 시각(6시 기준 초)으로 닫음
  - `isRunning=false`, `startTimestamp=null`
  - 소켓 `emitTimerStatus('idle')`
- 재개
  - 별도 resume 함수 없이, `isRunning=false` 상태에서 다시 시작 버튼(`toggleTimer`) 또는 과목별 시작 버튼(`startForSubject`)으로 새 세션 시작
  - 즉 "중단 세션 이어붙이기"가 아니라 새 세션 append 방식

### 2) 화면 이탈(탭 이동/백그라운드) 시 타이머 상태 유지 방법

- UI 표시 시간
  - `LiveElapsedTicker`에서 `setInterval(1000)` 사용
  - 하지만 값은 단순 +1초 누적이 아니라 매번 `Date.now() - startTimestamp`로 재계산
  - 즉, 렌더 tick은 interval, 경과시간 기준은 `Date.now()` 기반
- 실행 상태 보존
  - 상태는 `timerRuntimeStore`(메모리 전역 store)에 동기화
  - 화면 포커스 아웃 시 countdown 기준시각을 store에 저장하고, 복귀 시 이를 기준으로 remaining 재계산
- 백그라운드 진입 시
  - `persistTimerSnapshot('app-background')`로 서버 저장 시도
  - 로컬 알림(`showTimerRunningNotification`) 발행

### 3) AppState 변화(active/background/inactive) 처리 여부

- 처리 있음 (`timer.jsx`에서 `AppState.addEventListener('change', ...)`)
- `inactive/background` 진입 시
  - 진입 시각 기록
  - 당시 실행 중 여부 기록
  - 스냅샷 저장 + 실행 중 알림 노출
- `active` 복귀 시
  - 백그라운드 체류가 15분 이상이면(`TIMER_BACKGROUND_AUTO_CLOSE_MS`)
    - `POST /api/timer/session/close-incomplete` 호출
    - 프론트에서도 현재 세션 종료/정지 처리
    - idle 상태 emit + 안내 토스트 출력
- 추가로 day change 체크도 AppState active 복귀 시 수행

### 4) 과목별 시간 vs 전체 시간 계산/저장 위치

- 전체 시간
  - 프론트: `pauseTimer` 시 `Date.now() - startTimestamp`를 `totalElapsedMs`에 누적 계산
  - 저장: `saveDayToDb`를 통해 `/api/timer/day`로 전송
  - 서버: 세션 합으로 `total_elapsed_ms`를 재계산해 최종 저장(프론트 값은 신뢰하지 않음)
- 과목별 시간
  - 프론트: `displaySessions.filter(subjectId)` 후 `getSessionDurationMs` 합산으로 화면 표시 계산
  - 저장: 과목별 합계 숫자를 별도 저장하지 않고, 세션 단위(`study_sessions`) + 과목 메타(`timer_subjects`)로 저장
  - 즉, 과목별 합계는 조회 시점 계산형

### 5) 세션을 백엔드에 저장하는 시점

- 주 저장 API: `saveDayToDb` -> `POST /api/timer/day`
- 저장 트리거
  - 상태 변화 autosave: `sessions/subjects/tasks/totalElapsedMs` 변경 후 1초 디바운스 저장
  - 일시정지 직후 조건부 백업: 최소 간격(5분) 또는 누적 변화량(60초) 이상일 때 저장
  - 앱 background 진입 시 즉시 저장 시도
  - dayKey 변경(날짜 경계) 직전 flush 저장
- 별도 세션 정리 API
  - 백그라운드 복귀가 길면 `POST /api/timer/session/close-incomplete` 호출
- 소켓
  - 시작/정지 시점에 `friend_timer_status(studying/idle)` 이벤트 전송
  - heartbeat는 1분 주기로 송신(세션 저장 목적이라기보다 상태 유지/실시간 신호)

### 6) 공부기록 표(색칠 기능) 데이터 로드/색칠 기준

- 타이머 화면 내부 "공부 기록" 표(시간표형)
  - 데이터 소스: `displaySessions`(오늘은 live state, 과거 날짜는 `GET /api/timer/day` 로드 데이터)
  - 렌더 기준:
    - 06:00~다음날 05:59를 24x6 슬롯(10분 단위)로 분할
    - 각 세션의 `[startSeconds, endSeconds]`와 슬롯 겹침 비율 계산 후 segment 색칠
    - 색상은 `subject.color` 우선, 없으면 세션 스냅샷 `subjectColor`, 없으면 기본 회색
- 학교 화면 "잔디맵" 색칠
  - 데이터 로드:
    - 우리학교: `GET /api/schools/me/study-grass`
    - 다른학교: `GET /api/schools/:schoolId/study-grass`
    - `series`를 `{ dayKey, totalElapsedMs }`로 매핑
  - 색칠 기준:
    - `totalElapsedMs -> hours` 변환 후 구간별 색상
    - 0.5h 미만은 빈 칸, 이후 0.5/1/2/3/4/5h+ 레벨로 색 강도 증가
  - 맵 범위:
