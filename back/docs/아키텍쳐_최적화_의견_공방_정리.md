# 아키텍쳐 최적화 의견 공방 정리

작성 목적: `아키텍쳐 최적화 계획.md`를 바탕으로, **클루드 의견**과 **추가 반론/보완 의견(커서 분석)**을 한 문서로 통합 정리한다.

---

## 1) 공통 합의 사항 (서로 동의한 부분)

### 1-1. 인기검색어/해시태그 조작 방지 필요
- Redis `ZINCRBY`만으로는 순위 조작(매크로/반복 요청)에 취약.
- 사용자 증가 전이라도 최소한의 rate-limit/중복 카운트 제한이 필요.

### 1-2. 배치 안정성은 필수
- 잔디 집계/인기 집계 배치가 실패해도 조용히 넘어가면 운영 장애로 이어짐.
- 실패 알림, 재시도, 중복 실행 방지(lock/idempotency) 필요.

### 1-3. Docker Compose replicas 문법 주의
- `deploy.replicas`는 일반 compose에서 기대대로 동작하지 않을 수 있음.
- Swarm/ECS 전환 전에는 Nginx upstream + 다중 컨테이너 방식으로 명확히 구성 필요.

---

## 2) 쟁점별 공방 정리

## 쟁점 A: 지금 당장 무엇이 가장 급한가?

**클루드 주장**
- 위치정보 법적 이슈가 최우선.
- 좌표 저장 정밀도 완화, 개인정보 처리방침 보강 등 컴플라이언스 선행 필요.

**커서 보완 의견**
- 동의. 단, 법적/정책 작업과 성능 최적화(캐시, 배치 안정화)는 병렬로 추진 가능.
- 우선순위는 `법적 리스크 제거`를 1순위로 두되, Redis 캐시/알림 자동화는 1주 내 동시 진행이 효율적.

**결론**
- 최우선: 위치정보 취급 정책 정리(저장 정밀도, 보관주기, 고지 문구).
- 병행: Redis 캐시 + 배치 실패 알림 자동화.

---

## 쟁점 B: Redis 운영 방식 (로컬/자체 vs 매니지드)

**클루드 주장**
- 현재 Docker Redis가 이미 있으므로 Upstash 같은 매니지드 Redis는 지금 단계에서 과투자.

**커서 보완 의견**
- 동의. 초기에는 자체 Redis(단일 인스턴스)로 충분.
- 다만 장애/유실 대응을 위해 RDB/AOF 정책, 복구 절차, 키 TTL/네임스페이스 규칙은 반드시 문서화해야 함.

**결론**
- 현 단계: 자체 Redis 유지.
- 전환 조건: 서버 다중화/운영 인력 부족/가용성 요구 상승 시 매니지드 검토.

---

## 쟁점 C: 배포 인프라 선택 (Hetzner vs AWS 등)

**클루드 주장**
- Hetzner는 가격 대비 성능이 매우 좋고 현실적 대안.
- 단, 국내 대상 서비스는 지연시간 비교 필요.

**커서 보완 의견**
- 동의. 비용만 보면 Hetzner 우위가 크지만, 사용자 체감과 운영 편의(서울 리전, 매니지드 서비스)는 AWS가 강점.
- 최종 선택은 `월 예산` + `지연시간 테스트 결과` + `운영 자동화 수준`으로 결정하는 것이 타당.

**결론**
- 후보 1: Hetzner 단일 VPS + Docker (최저 비용)
- 후보 2: AWS Lightsail/EC2 소형 + 점진적 매니지드 전환 (운영 편의)
- 반드시 선행할 것: 동일 API 기준 지연시간/가용성 비교 테스트.

---

## 3) 커서 분석에서 추가로 강조한 운영 필수 항목

### 3-1. 관측(Observability) 자동화
- p95/p99 latency, DB slow query, Redis hit ratio 대시보드.
- 임계치 알람(5xx 급증, Redis 메모리 80%+, 배치 실패).

### 3-2. 배치 운영 표준
- 재시도 정책(backoff), 중복 방지 락, 백필(backfill) 잡.
- 작업 성공/실패 로그 집계 및 알림 연동.

### 3-3. 캐시 정합성 정책
- 캐시 invalidation 트리거(생성/수정/삭제) 명시.
- Redis 장애 시 복구 루틴(재생성 잡) 정의.

---

## 4) 클루드 측 추가 주장 중 반영 권고

### 4-1. 위치정보 법적/정책 항목 (강력 권고)
- 좌표 정밀도 완화 저장 정책(예: 격자화/소수점 제한 등).
- 보관 기간, 파기 기준, 접근 권한 통제.
- 개인정보 처리방침에 위치정보 항목/목적/보관기간 명시.

### 4-2. 단계별 과투자 방지
- 현재 트래픽 규모에서 매니지드 서비스 다건 도입은 비용 비효율 가능.
- 먼저 캐시/배치/알림 자동화로 병목 제거 후 증설 판단.

---

## 5) 통합 실행 우선순위 (합의안)

| 우선순위 | 작업 | 기대 효과 | 비고 |
|---|---|---|---|
| 1 | 위치정보 저장/정책 정비 | 법적 리스크 감소 | 문서 + 저장 정밀도 정책 |
| 2 | Redis 캐시 적용(GEO/ZSET/Bitmap) | DB 부하 감소 | 기존 스택 유지 |
| 3 | 배치 실패 알림 + 재시도 | 운영 안정성 확보 | 슬랙/디스코드 웹훅 |
| 4 | 로컬 탈출 배포(VPS 우선) | 가용성/접근성 개선 | Hetzner vs AWS 비교 |
| 5 | 인기지표 조작 방지 | 데이터 신뢰성 향상 | rate-limit/중복 제어 |
| 6 | 관측/알람 대시보드 | 장애 조기 탐지 | p95/오류율/캐시미스 |

---

## 6) 최종 요약

- 기존 최적화 방향(Redis 중심)은 맞다.
- 여기에 `위치정보 법적 대응`, `배치 안정성`, `관측 자동화`를 추가해야 실서비스 운영 계획으로 완성된다.
- 배포는 당장 고비용 매니지드로 갈 필요 없이, **저비용 VPS 기반**으로 시작하고 지표 기반으로 확장하는 전략이 가장 현실적이다.
